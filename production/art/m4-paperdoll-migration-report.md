## 4. Dependency Audit

**Method**: `grep -rni "paperdoll"` across `Source/`, `Content/`, `Config/` (550 matches before and after — unchanged, since no C++/Config file was touched), plus targeted searches for each of the 12 filenames and for the 4 `Visual_*` IDs.

**Findings**:

- A real runtime Paperdoll system exists: `UPAPaperdollComponent`, `FPAPaperdollModel`, `FPAPaperdollConstants` (`Source/ProjectAscendant/{Public,Private}/Character/PAPaperdoll*`). Socket constants in C++ (`HelmCrestLocation = (64,40)`, etc., per `PACharacterVisualIdentityTests.cpp`) match the master-rig metadata exactly — confirming the 128×128 rig convention is the correct target, not a separate system.
- `EPAPaperdollLayer` enum defines exactly 5 slots: `BaseBody`, `ChestArmor`, `Helmet`, `MainhandWeapon`, `OffhandShield`.
- `PAItemStaticDataAsset.cpp` assigns `PaperdollVisualId` as a **symbolic `FName`** (`"Visual_IronArmor"`, `"Visual_StarterCloth"`, `"Visual_LeatherRanger"`, `"Visual_ArcanistRobe"`) — these 4 IDs map 1:1 to the 4 male `T_Hero_*.png` files by name.
- **Critically: no code path resolves `PaperdollVisualId` → an actual texture/asset path.** `FPAPaperdollModel::EquipVisual`/`GetActiveVisualAssetId` only track which `FName` is active per layer; there is no `TMap<FName, UTexture2D*>`, DataTable, or soft-object-path lookup anywhere in the codebase. This matches the epics index's own status for this system: *"Code Complete, Art in Placeholder-Tier."*
- Consequence: none of the 12 legacy filenames are referenced by path anywhere in `Source/`, `Content/`, or `Config/` — zero direct references, before or after this package's changes. It was therefore safe to place normalized production output at a **new** path (`Content/Art/Characters/Paperdoll/`) without touching any C++ reference, per the package's own safety rule (§3 of the spec: prefer a new path over destructive replacement when no direct reference exists to preserve).
- **No gender/body-type field exists anywhere** in `PAPaperdollTypes.h` or `PAPaperdollComponent.{h,cpp}` (checked for `gender`, `Female`, `Male`, `BodyType`, `Sex` — zero matches). The `character-visual-system.md` GDD does not document a gender system either. This is why the 4 `Female_Female_*` files are `REVIEW_REQUIRED`, not `NORMALIZE`: there is no runtime slot for them to migrate into, and inventing one would be architecture work far outside this package's scope.
- `PAItemStaticDataAsset.h` has a separate `TSoftObjectPtr<UTexture2D> IconTexture` field, distinct from `PaperdollVisualId`. The 4 `Thumb_T_Hero_*.png` (512×512, cropped/framed differently from the body layers — see §9) correspond conceptually to this `IconTexture` slot, not to the master-rig body layer. Running them through the 128×128 rig-alignment pipeline would misapply body-layer conventions to what is actually a different asset class (an inventory icon).

### Architectural note (documented, not silently expanded)

All 4 male source illustrations bake a specific held weapon/shield into the same image as the chest armor (e.g. `T_Hero_IronArmor.png` includes a drawn sword + shield; `T_Hero_LeatherRanger.png` includes a dagger + bow). The runtime model treats `MainhandWeapon`/`OffhandShield` as **independent** layers from `ChestArmor`. This package migrates the legacy art **as-is** (preserving its existing visual identity, per the package's core directive) but flags that these `ChestArmor` production outputs are not yet truly modular with respect to weapons/shields — a future package will need to address this before the Paperdoll system can compose weapon choice independently of armor choice. This is a pre-existing property of the legacy source art, not something introduced by this migration.

## 5. Normalization Methodology (Before/After)

The 4 source files are continuous-tone illustrations (1024×1024, 27K–66K colors, thousands of semi-transparent edge pixels) — not native pixel art, the same situation the M2 armor package encountered at 256×256. The same category of correction was required: isotropic downsample + palette quantization + binary alpha, reusing `map_to_official_palette()` and `OFFICIAL_4TONE_PALETTE` already defined in the pipeline (no new palette invented).

**Alignment method** (implemented in `normalize_paperdoll_layer()` / `measure_paperdoll_anchors()` in `Tools/Aseprite/aseprite_export_pipeline.py`): per-asset anchors were **measured from real alpha-channel data**, not assumed uniform or guessed from the bounding box:

- `source_head_top_y` / `source_foot_bottom_y`: topmost/bottommost row with alpha > 128.
- `source_center_x`: horizontal centerline of the head/neck band only (average of a mid-hair row scan and the head-band center of mass) — **not** the full silhouette bbox center, which is skewed by asymmetric held props (shield, bow, staff). This was verified empirically: 3 of 4 assets measured center_x within 2px of each other (~525–528), while `ArcanistRobe` measured ~100px further right (~617) — a real per-asset placement difference in the source art, correctly detected rather than assumed away.
- Scale factor `S = (114 − 34) / (source_foot_bottom_y − source_head_top_y)`. The head-top target of Y=34 was chosen because, combined with the rig's own `foot_pivot=114`, it implies a waist position at `34 + 0.575×(114−34) ≈ 80` — matching the rig's documented `waist_seam_y=80` almost exactly, without needing to guess a source-image waist pixel row (which varies visually by 60+px across garments — robe belts sit higher than armor tassets — even though the underlying body anatomy is identical).
- The full 1024×1024 canvas is uniformly scaled (LANCZOS, isotropic — no stretching) and pasted onto a transparent 128×128 canvas at the computed offset, then every pixel is thresholded (`alpha ≥ 128` → opaque, mapped to nearest official-palette color; else fully transparent) — mirroring the exact armor-rework approach from M2.

All 4 outputs land their silhouette bottom row within 1px of the target foot pivot Y=114 (an inherent ~1px softening from LANCZOS downsampling at 128× reduction, documented and tolerated — see §6 Art Gate note), and their head-top consistently at Y=35 (1px below the 34 target, same cause). Foot X position differs naturally per asset (a bipedal figure in an action stance does not plant both feet under the spine centerline) — this is correct, not a defect.

**Visual QA**: all 4 outputs were rendered at 6× nearest-neighbor scale and visually inspected — silhouettes are clean and legible, character identity/pose/equipment are preserved, colors map coherently to the existing steel/gold/leather/blue ramps already used for weapons and armor. One minor, non-blocking observation: `PD_Hero_StarterCloth`'s tan cloth and skin tones sit close together in the reused armor palette (both drawing from the Leather/Skin ramps), producing slightly less contrast between tunic and forearm than in the source art — noted for a future palette-refinement pass, not a rework blocker.

## 9. Notes for the next package (icons / gender)

Not part of this package's deliverable, recorded for planning:

- **Icons**: the 4 `Thumb_T_Hero_*.png` (512×512) are framed/cropped as centered square portraits, distinct in composition from the 1024×1024 body layers, and conceptually target `PAItemStaticDataAsset::IconTexture`, not a Paperdoll rig layer. A future icon-migration package should establish the project's actual UI icon convention (dimensions, palette rules) before normalizing these — none is currently documented, and armor/weapon icons currently double as the 32×32 equipment sprite itself rather than following a separate dedicated icon spec.
- **Gender/body-type**: 4 `Female_Female_*` source files exist and appear production-quality on visual inspection, but there is no `EPAPaperdollLayer`/`FPAPaperdollModel` support for a second body type. Migrating them now would require inventing an unreleased feature, explicitly out of scope (§20 of the task spec: "Do NOT invent a new coordinate system" / architecture).
